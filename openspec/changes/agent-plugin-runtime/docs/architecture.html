ClipForge 插件运行时 · 整体架构

白话拆解:每一层是干什么的

整张图就一句话:外面的 AI 隔着传达室下单,里面的数据只从一个传菜窗口进出,插件各住各的包间,谁也搞不垮宿主。控制流从左往右,数据经 ctx 桥时只传副本。

外部 Agent
住在别的 App 里的 AI 助手(比如 Claude Code)。它只能隔着传达室(MCP 网关)下单:搜历史、复制条目、装插件。进不了后厨。
pi Agent
住在 App 自己窗口里的 AI 面板。它不走传达室,直接喊后厨(invoke 直调),所以快——这是现有热路径,插件机制一行不改。
设置页
你操作的地方:装/卸插件、改配置、管提示词模板。装插件和改配置都要你点确认,Agent 不能替你拍板。
MCP 网关
传达室。墙上挂着两块菜单:固定菜单(40 条 clipf.* 工具)和插件自报的菜(plugin.*.*)。外部 Agent 只能照菜单点。
plugin_runtime 门面
插件管理处。每个插件一份档案加一条生命周期(cordis Fiber):装 → 跑 → 停 → 回收,全自动;插件挂了标记 Failed,不连累别人。
ctx 桥(图上红框)
唯一的传菜窗口。插件在 manifest 里声明过要什么,窗口里才有什么;没声明的菜,窗口里压根不存在。数据只传副本,超时、限量、双层看门狗都在这层把守。
域层
后厨。剪贴板采集、搜索、打标签、SQLite 存取全在这。插件要数据只能经窗口点菜,不能翻墙进后厨。
插件沙箱
独立包间。一个插件一个线程一个 QuickJS,内存封顶(默认 8MB)。包间里跑死循环、爆内存,只死自己;宿主把它强制回收、停成 failed,重新启用才复活。
